# Data Hygiene — Never Publish Org-Identifying Data

Behavior-trigger rule. Same shape as the global force-push abort signal
and orc `tooling-friction.md`. Names the *behavior*, not the concept,
because concepts are easy to rationalize past at the keystroke.

sidestep operates against a StepSecurity organization bound to a real
company. Its payloads, audit trail, and fixtures can name the org, its
repositories, its people, and its security posture. sidestep is a
**public** repo — a leak here exposes internal structure to anyone.

## The trigger

You are about to put text into a **durable, shareable channel** — a git
commit message, a file being committed, a `gh issue`/`gh pr` body or
comment, a PR description, a discussion post, a published artifact, or
any log/transcript you paste outward. STOP and scan that text for the
forbidden classes below before it lands.

Also stop when about to: paste live `sidestep` output or an audit line
"to illustrate"; regenerate a fixture from a real API response; write a
test whose expected value is a real org/repo/email; put a real
`--owner`/`--customer`/`--param` value in an example or doc.

## Forbidden in any durable/shareable channel — NEVER

1. **Org / customer identity** — the real GitHub org or customer slug,
   internal team names, anything that names the company.
2. **Internal repository names** — real repo names reveal the product
   and infra map. Use synthetic (`web-api`, `auth-svc`, `media-svc`,
   `ctf-engine`, `svc-infra`).
3. **PII** — user names, emails, team memberships from audit-log actors
   or customer-admin records.
4. **Security posture tied to the org** — which repos have which
   detections/policies, suppression reasons, threat-intel incidents.
   (An abstract detection pattern is fine; "org X repo Y has detection
   Z" is a map of their weak points.)
5. **Credentials** — StepSecurity API tokens, any bearer/key material.
6. **Raw audit-trail lines** — they carry real path/query param values
   (owner, customer, repo), local hostname/username, and predicate text.

## The fix — sanitize before the keystroke

- Prefer **shapes over values**: `ops show <id>`, exit codes, error
  text, `shape_hash` — not payloads.
- Reproduce against **wiremock + `examples/fixtures/`** (synthetic). A
  repro on synthetic data is directly committable as a failing test.
- If real output is unavoidable, substitute: org/customer → `acme-corp`;
  repo → `web-api`; user → `user@example.com`; delete pagination
  cursors.
- Fixtures are synthetic **by policy** — never regenerated by copying
  live payloads.

## Backstops (defense in depth — not a substitute for the rule)

- `scripts/check-org-leaks.sh` runs in pre-commit (lefthook) + CI.
  Generic patterns are in-repo; org literals go in a **gitignored**
  `.leak-patterns.local` (create one per machine that touches a real
  org — put your org slug, real repo names, and internal emails there).
- GitHub secret scanning + push protection are enabled on the repo.

The hooks catch key material and your declared literals. They do NOT
catch an undeclared repo name or email — those are on you at the
keystroke. That's why this is a behavior rule, not just a scanner.

## Why this rule exists

sidestep's fixtures originally carried the real company name and real
internal repo names (`clip-*`, etc.) into a public repo — caught by a
fleet-wide scan, sanitized to synthetic values 2026-07-15 (working
tree; history retains the originals — see the git-filter-repo plan in
that session's harvest). This rule moves the guard in front of the
keystroke so it doesn't recur. Sibling of bloomctl's
`tenant-data-hygiene.md` (same shape, MDM-tenant variant).
